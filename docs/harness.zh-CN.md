# Harness：AI 时代的工程底座

## 0. Harness 是什么，为什么需要它

**一句话定义：Harness 是让 AI 能独立完成"写代码 → 跑起来 → 看结果 → 发现错误 → 自己修正"这个闭环所需要的全部工程设施。** 它包括五个部分：工程脚手架、基础设施、文档体系、可复用组件、统一的操作入口。

### 0.1 从一个式子出发

模型在项目里的有效能力，取决于三个因素：

> 有效能力 = f(模型本身, 上下文, **反馈回路**)

模型本身我们无法改变；上下文（文档、提示词）的边际收益正在下降——模型越强，事先告诉它的必要性越低。真正的杠杆在第三项：**反馈回路**。模型能不能自己把服务跑起来？能不能自己看到测试红灯？能不能自己查日志定位错误？这些决定了问题是"模型自己发现、自己解决"，还是"回流到人"。

Harness 的全部投资都押在反馈回路上。这与"设计决策"的开发方式是一体两面：设计决策（PTA：PD 产品底线 + TD 技术决策 + AC 验收标准，文档形态见 7.5）定义"什么算对"，Harness 回答"怎么知道对不对"。没有 Harness，AC 写了没法验，模型撞了坑没有证据——契约就是空头支票。

### 0.2 两条链：探索链与裁决链

整个 Harness 体系贯穿一个总原则：

> **保真度是按"这个阶段要发现什么"分配的资源；唯一的硬约束是：裁决链上不许有假。**

- **探索链**：目的是尽早发现"还没定下来的决策"。典型活动是 Demo。这条链上允许使用假后端（Mock），因为速度和可控性比真实性重要——但假必须是声明过的假，且它的结论只用于确认产品决策，不用于判定系统正确。
- **裁决链**：目的是判定"系统是否正确"。典型活动是测试、验收、部署。这条链上一切必须是真的：真数据库、真对象存储、真链路，证据必须可归属到本次执行。

为什么本地开发禁用 SQLite 顶替 MySQL，却允许 Demo 用假后端？界线就在这里：SQLite 的问题不在于假，在于**它假装自己的绿灯有裁决效力**——本地过了你就信了，然后生产挂了；而 Mock 的绿灯从不主张任何东西，它碰过的每条链路最终都会被真实环境上的测试重新裁决。

## 1. 五条总原则

后面所有章节的具体决定，都是这五条原则的推论。

1. **反馈回路判据。** 每一项 Harness 设施都必须能回答："它缩短了哪条反馈回路？让模型少问了人几次？"答不上来的设施是仪式，不做。
2. **拉动式建设。** 设施由真实项目的真实需要拉动，不由平台愿景推动。原则可以先写（写文档便宜），通用机制必须先在真实项目里活过一次，验证后再沉淀（建框架贵）。
3. **裁决链上不许有假。** 探索可以用假后端、假数据；判定正确性时必须同构、必须真实、证据必须属于本次执行。
4. **结构即提示。** 对模型来说，示例的效力大于指令：存量代码的结构就是权重最高的提示词。因此架构约束优先固化进脚手架和自动门禁，而不是写在文档里要求模型"遵守"。
5. **裁判与运动员分离。** 执行可以全部交给模型，但判定标准（什么算对、什么算不合格）必须在执行之前定好、锁死，不允许执行者事后挑选有利证据或降低标准。

## 2. 脚手架：语言与工程基线

脚手架是新项目的起始工程模板。它决定最基础的工程闭环、抽象方式和代码分层。脚手架不是把某个业务项目复制一份删掉业务代码，而是经过真实项目验证、可持续演进的干净基线。

> **注意：本章的具体选型（Vben Admin 5、Electron、FastAPI 及相关工具链）是当前实践下的举例，不是 Harness 的固定组成部分。** Harness 约束的是不变的东西——每种应用形态要有经过真实项目验证的基线、基线要覆盖从初始化到部署的完整闭环、约束要固化进脚手架而非文档。至于具体选什么语言和框架，实践时由架构师根据项目场景亲自决定，并对选型负责。

### 2.1 前端后台：Vben Admin 5

中后台项目默认采用 Vben Admin 5（Vue 3 + Vite + TypeScript）作为初始化基线。保留布局、路由菜单、登录与权限、请求层、类型检查、单元测试、E2E 和构建部署能力；按项目需要删除多余的 UI 实现、Mock、Playground 和演示页面。

### 2.2 桌面端：Electron / SwiftUI

Windows 和 macOS 默认采用 Electron；只有产品明确仅支持 macOS、且强依赖原生系统能力时才选 SwiftUI。Electron 采用"轻量构建底座 + 生产能力加固"的内部脚手架：

- 以 `@quick-start/create-electron` 的 Vue 3 + TypeScript 模板为初始底座，使用 `electron-vite` 分别构建 Main、Preload 和 Renderer。它是开发与构建基线，不直接视为生产完成态。
- 使用 `electron-builder` 生成 Windows NSIS 和 macOS DMG/ZIP 产物；使用 `electron-updater` 提供 `internal / beta / stable` 三条升级通道；完成 Windows 代码签名、macOS 签名与公证。
- 安全基线默认启用 `nodeIntegration: false`、`contextIsolation: true`、`sandbox: true` 和 Electron Fuses。按窗口划分最小权限的 Preload API，不向 Renderer 暴露原始 `ipcRenderer`；IPC 需要发送方校验、参数校验和严格 CSP。
- 默认配置 Vitest 单元测试、Playwright Electron E2E 和打包后冒烟测试。Windows 与 macOS 分别在各自的原生 CI Runner 上构建、安装、验证，不用单平台交叉构建的结果代替真机验收。
- 从真实产品持续吸收窗口管理、托盘、协议、安全存储、日志、自动升级和发布经验；`uxc_chat` 作为生产能力参考库，但不通过复制整个业务项目来生成脚手架。

### 2.3 后端：Python / FastAPI

后端采用 Python + FastAPI，以"官方工程底盘 + Benavlabs 模块结构 + 真实项目经验"三者组合建设内部脚手架：

- 工程底盘参考官方 Full Stack FastAPI Template：保留后端初始化、环境配置、Docker Compose、数据库迁移、自动化测试、CI 和部署闭环；其自带的 React 前端不采用，由 Vben Admin 5 替代。
- 代码组织参考 Benavlabs FastAPI Boilerplate：采用 `interfaces / infrastructure / modules` 三层结构，按业务能力组织垂直模块。每个模块拥有自己的 `routes / schemas / service / repository / models`，避免所有 API、Service、Repository 各自堆成一个大目录。
- 生产能力采用 SQLAlchemy 2.0、Alembic、Pydantic Settings、Redis、后台任务、结构化日志、健康检查、单元测试和基于真实依赖的集成测试。
- 吸收真实项目已验证的日志上下文、任务生命周期、数据库韧性、发布产物与运行证据经验，统一接入 `run / observe / drive / deploy` 操作面（见第 6 章）。
- 明确取舍：只用 SQLAlchemy 2.0，不同时保留 SQLModel；首个版本只正式支持一种数据库；从干净的新仓库建设脚手架，不通过"复制业务项目再删业务代码"生成。

### 2.4 维护原则

按应用形态维护少量脚手架工程，随真实项目的开发持续沉淀迭代。脚手架既用于新项目初始化，也是架构、验证和交付方式的参考实现——这正是"结构即提示"：模型进入新项目后模仿的第一个对象就是脚手架本身。

## 3. 可执行架构：设计原则如何落地

设计的本质是隔离变化、解耦依赖、约束复杂度，让新能力尽量通过"增加局部实现"完成，而不是反复修改已经稳定的核心代码。Harness 不在文档里要求 AI"遵循设计原则"，而是把依赖方向、扩展点、黄金路径、合同测试和架构门禁固化在脚手架中，形成**可执行架构**——违反原则的代码应该被门禁拦住，而不是被评审发现。

### 3.1 七大设计原则

1. **单一职责（SRP）**：一个模块只应有一个主要的变化原因。职责按业务能力和变化方向划分，不机械追求"一个函数一个文件"。
2. **开闭原则（OCP）**：对扩展开放，对修改关闭。新增类型时优先新增模块、策略或注册项，不在稳定核心里追加 `if / switch`。
3. **里氏替换（LSP）**：实现类必须能替换其抽象类型：不隐式收紧输入、不放宽错误、不破坏返回语义。
4. **接口隔离（ISP）**：调用方不被迫依赖它不需要的能力。接口围绕具体使用场景保持小而聚焦。
5. **依赖倒置（DIP）**：高层业务依赖稳定抽象，不直接依赖数据库、供应商 SDK 或具体框架。外部能力通过 Port / Adapter 接入（Port 是插座——业务定义的稳定接口；Adapter 是插头——某个具体供应商的实现），在 Composition Root 统一组装。
6. **迪米特法则（LoD）**：模块只与必要的直接协作者交互，不穿透多层对象、不操作其他模块的内部细节。
7. **合成复用（CRP）**：优先用组合和委托复用能力，只在存在稳定"is-a"关系且满足里氏替换时用继承。

七条是判断方向，不是七道机械门禁。抽象强度由真实变化点决定：在 Provider、存储、业务模块、工作流执行器、平台适配这类高概率变化的位置预留稳定扩展点；对只有一个实现、低概率变化的简单业务保持直接，不为"用上设计模式"制造多余的 Interface、Factory 和 Manager。

### 3.2 案例：可扩展的 AI 图片 Provider

需求：同一个生图业务可以使用 UXC、OpenAI 或未来新增的供应商。业务 Service 不直接调用任何具体 SDK，而是依赖稳定的 `ImageProvider` Port；每个供应商提供自己的 Adapter，并通过 Registry 注册。

```text
ImageGenerationService
        ↓ depends on
   ImageProvider Port
      ↙          ↘
UXCImageAdapter   OpenAIImageAdapter
        ↘          ↙
       Provider Registry
```

- **SRP**：Service 只编排生图用例；每个 Adapter 只处理一个供应商的认证、请求和响应映射。
- **OCP**：新增供应商 = 新增 Adapter + 注册项，不改核心流程。
- **LSP**：所有 Adapter 遵守同一套输入、输出、错误、超时和取消合同，可安全互换。
- **ISP**：文生图、图生图、任务查询、取消可按真实能力拆分 Port，不强迫供应商伪造不支持的方法。
- **DIP**：业务层只认 Port；SDK 和 HTTP 细节在外层 Adapter。
- **LoD**：Service 只与 Port 交互，不穿透 Adapter 去读 SDK Client 或认证头。
- **CRP**：Service 通过组合获得 Provider、日志、计费、存储能力，不继承庞大基类。

扩展点的黄金路径固化为："新增 Adapter → 注册 → 跑统一合同测试 → 用确定性 Fake 完成开发验证 → 收口阶段跑少量真实 Provider 验收"。如果新增一个 Provider 仍需要同时改业务 Service、UI、存储和多处 `switch`，说明扩展点设计或脚手架约束不合格。

**这一章还有一个副产品：Port/Adapter 正是第 5 章 Mock 的物质基础。** 每个 Port 天然可以配一个 Fake Adapter——探索链上的假后端不需要额外发明机制，换个插头就是。

## 4. 基础设施：同构环境

### 4.1 为什么禁"伪平替"

模型的自主性依赖反馈的保真度。如果本地用 SQLite、生产用 MySQL，"本地能跑"这个反馈就是失真的——模型自查会失效，问题回流到人，整个分工塌掉。所以：**开发与生产必须保持引擎、主版本、客户端、协议、Migration 和业务代码一致；环境差异只允许存在于地址、凭证、容量、单机/集群拓扑和托管方式。**

本地不需要复制生产的主从、集群、跨区容灾和大容量，但必须消除"本地能跑、生产语义不同"。基础设施镜像固定版本，禁止 `latest`；服务通过 Docker Compose 启动，提供健康检查、持久化 Volume 和显式清理入口。

### 4.2 最小基础设施

- **数据库：MySQL。** 本地与生产同主版本、同驱动、同 SQLAlchemy 模型；业务代码不提供 SQLite 降级路径。
- **缓存与轻量任务：Redis。** 本地与生产同主版本。每个项目必须明确 Redis 分别承担缓存、锁、限流还是任务队列，避免同一 Key 空间混用不同语义。
- **对象存储：腾讯云 COS。** 本地、测试、生产统一使用 COS，以开发桶、测试桶、生产桶隔离环境。每个 Bucket 以 `main/` 为正式根目录；业务数据只保存相对 Object Key，统一调用 `CosStorage`，由 `COS_ROOT_PREFIX` 把相对 Key 解析到当前根目录。组件集中处理上传、签名、路径、重试、超时、错误码和脱敏，但不为"将来换对象存储供应商"设计无谓的通用抽象。单元测试可用 Fake；集成测试和验收必须访问真实 COS。本地 Drive 运行前把开发桶 `main/` 服务端复制为一次性的 `clone-<run_id>/`，Drive 应用只允许读写该副本，取证后整体删除；测试与生产环境禁止创建副本前缀。
- **异步执行：Worker。** Worker 与 API 使用同一份领域代码、任务合同和配置模型，通过 Redis 传递任务、`trace_id` 和必要的幂等键（防止同一任务重复执行的唯一标识）。
- **大模型：LLM Proxy。** 作为独立通用服务维护，集中处理供应商适配、鉴权、路由、重试、限流、成本和 Provider Request ID，避免每个项目重复接入模型供应商。

### 4.3 Database Migration

Migration 是数据库结构的版本化演进脚本：建表、加字段、改约束、建索引、必要的历史数据转换，都必须形成按顺序执行、可审计的脚本：

```text
001_create_users
002_add_avatar_url
003_add_user_email_index
```

Harness 对 Migration 的要求：

- `run`：启动本地 MySQL 后，先执行未执行的 Migration，再启动应用。
- `drive`：仅在本地启动一次性 MySQL 实例，把受保护的本地 Schema 复制到临时实例，只在副本上执行 Migration 和测试操作。
- 测试：从空库完整执行全部 Migration，防止"只在开发者的历史数据库上能通过"。
- `deploy`：部署应用前受控执行 Migration；破坏性变更必须具备备份、兼容窗口和回滚方案，不能依赖应用实例启动时各自抢跑。

Python / SQLAlchemy 项目默认使用 Alembic。Migration 是数据库结构的唯一演进入口，禁止手工改库后只更新 ORM 模型。

### 4.4 Log 与 Trace

旧时代日志为人设计（人翻文件）；新时代日志首先为模型设计——结构化、单行、可按链路编号串起来。分层设计是："通用代码库负责生产证据，独立后端负责保存检索，Harness CLI 负责统一取证"，不自研需要业务代码同步调用的日志服务。

```text
业务应用
  ↓ 通用 Observability 代码库
单行 JSON stdout
  ├─ 本地：Docker Logs
  └─ 生产：腾讯云 CLS

harness observe
  ├─ 查询本地 Docker Logs
  └─ 查询生产 CLS
```

通用能力以统一规范和多语言实现维护：Python 提供 `harness-observability`，Vue / Node.js / Electron 提供 `@harness/observability`。代码库负责：

- 创建、解析、传播 `trace_id`（一次业务请求贯穿全链路的编号），通过 Middleware、Python `contextvars`、Node.js `AsyncLocalStorage` 自动注入日志上下文。
- 让 HTTP 请求、Redis 任务、Worker、LLM Proxy、COS 调用在同一业务链路中携带同一个 `trace_id`；COS 调用同时记录供应商返回的 Request ID。
- 输出单行结构化 JSON 日志，统一字段、事件命名、时间格式、错误堆栈和敏感信息脱敏。
- 默认输出 stdout，不在业务线程中同步调用远程日志服务——日志基础设施故障不能拖慢或阻断业务。

每条日志至少包含：

```text
timestamp、service、environment、level、event、message、trace_id
```

按场景增加：

```text
request_id、task_id、workflow_run_id、duration_ms、error_code、
provider_request_id、cos_request_id
```

本地查询不部署日志数据库，直接扫描近期 Docker Logs、筛选同一 `trace_id`、按时间排序——本质是一次有时间范围的遍历，适合本地小规模：

```text
harness observe trace <trace_id>
  → docker compose logs --since 24h
  → 筛选 trace_id
  → 按 timestamp 排序
  → 输出完整链路时间线
```

生产日志量大，通过腾讯云 CLS 为 `trace_id` 建字段索引后查询：`harness observe trace <trace_id> --env production` 调用 CLS 接口，返回与本地一致的时间线格式。对人和 AI 来说查询入口不变，只有底层数据源不同。

前端只上报关键用户动作和未捕获错误，不上传全部 `console.log`；后端用相同日志结构写入，保留前端生成或收到的 `trace_id`。将来若需要可视化 Span 树、自动采样、跨大量服务的性能分析，再在现有字段与传播规范之上引入 OpenTelemetry / Jaeger / Tempo——它们不是 Harness 的默认依赖。

### 4.5 Metrics

第一阶段不部署 Prometheus、Grafana。应用只需提供机器可读的两个端点：

- `/health`：进程、MySQL、Redis、Worker 和关键外部依赖的健康状态。
- `/metrics`：请求量、错误数、耗时、Worker 队列深度、任务成功/失败/重试、LLM 请求与 Token/成本、COS 上传错误等核心指标。

`harness observe metrics` 直接读取汇总。只有项目需要历史趋势、Dashboard、生产告警或多实例聚合时才引入专业 Metrics 后端。业务指标名称和标签提前保持稳定，禁止把 `trace_id`、`task_id`、`user_id` 等无限增长的字段作为 Metrics 标签。

## 5. 探索面：Demo 与 Mock

本章是探索链的主体。它回答的问题与裁决链相反：不是"系统对不对"，而是"产品该怎么做还有哪些没定下来"。

### 5.1 为什么需要探索面

产品决策和技术决策有对称的发现机制：

| | 技术决策 | 产品决策 |
|---|---|---|
| 发现机制 | 测试红灯（模型撞上） | Demo 体感（人撞上） |
| 沉淀形态 | AC 验收标准 | PD 产品底线 |
| 发现时机 | 实现过程中 | 写正式实现之前 |

技术坑由 AC 测试让模型自己撞出来；产品坑没有测试可跑，它的发现机制就是 Demo——很多交互决策（节奏、手感、延迟容忍度）只有"摸到"才能定。

Demo 必须做在**真实项目里**，而不是孤立 HTML。原因是成本结构变了：过去原型保真度与成本成正比，只买得起低保真原型，而低保真原型会撒谎——用不了真实组件库、真实路由、真实数据形状，验完的体感与上线体感是两回事。现在模型写代码便宜，真实项目里搭 Demo 的成本已经接近孤立 HTML，但保真度高一个量级：真组件、真路由、真请求层，只有数据是假的。**成本抹平之后，最高保真理应成为默认选项。**

这也不是旧式"原型驱动开发"（RAD）。旧原型有著名困境：扔掉重写（浪费）还是演进成正式版（原型质量差）。这个困境现在消失了：**决策保留，代码随缘**——PD 确认沉淀进设计决策，代码要不要复用让模型自己判断，都不亏。

### 5.2 什么时候必须做 Demo

不是所有前端需求都要 Demo。判据一条：**Demo 的价值 ∝ 未定产品决策的数量。**

- PRD 里的产品行为能全部用文字无歧义写清、没有"要试了才知道"的部分（如表格加列、表单加字段，交互被现有设计系统完全锁定）——Demo 可省。
- 只要存在未定的交互决策——Demo 必须。

不要把 Demo 变成流程门禁。把发现机制变成仪式，正是旧时代冗重 SPEC 的死法。

### 5.3 Mock 的定位：声明过的假

Demo 的形态是"纯前端 + 后端 Mock 的可交互闭环"。Mock 是假后端，它与 4.1 禁止的"伪平替"区别在于：

- 伪平替（SQLite 顶替 MySQL）出现在**裁决链**上，它的绿灯被当作正确性证据——这是危险的谎言。
- Mock 只出现在**探索链**上，是声明过的假：它的结论只用于确认产品决策，永不进入正确性判定；它碰过的每条链路，最终都由 AC / E2E 在真实后端上重新裁决。

实现上，Mock 不需要发明新机制：请求层已按 DIP 做了 Port 化，Mock 就是每个 Port 的一个 Fake Adapter，切到真实后端就是换 Adapter。目标形态是脚手架自带 `run --mock`，一键启动纯前端闭环。

### 5.4 四项注入：决策覆盖，不是环境仿真

Mock 不能是"返回假数据"，必须是**可编程的假后端**——能按需注入四类条件。注意：注入的目的不是把环境模拟得更真，而是防止 Demo 系统性漏掉四类产品决策：

| 注入 | 逼出来的产品决策 |
|---|---|
| 延迟 | 要不要加载态？乐观更新还是转圈？多少毫秒内没反馈用户会再点一次？ |
| 错误 | 错误怎么提示？可重试吗？半途失败停在哪个状态？ |
| 空态 | 首次进入看到什么？空页面引导做不做？ |
| 极端数据 | 长文本截不截断？两千条列表分页还是虚拟滚动？ |

不注入延迟的 Demo，等于替你决定了"这个产品没有加载态设计"——只是你不知道自己做了这个决定。Demo 验收必须至少过一遍非正常路径的体感。

### 5.5 Demo 收口：产出是决策，不是代码

在真实项目里做 Demo 的副作用是没有天然的丢弃点，临时代码会默默转正。因此 Demo 结束必须有显式收口：

1. 产出**确认过的 PD 清单**和**交互层的 AC**，写进设计决策。
2. **显式决定**Demo 代码哪些保留、哪些重写——不允许默认全部转正。

记住：Demo 的交付物是决策，代码复用是副产品。

### 5.6 建设方式：立原则，不建框架

本章遵守总原则第 2 条（拉动式建设）：现在确定的是原则——Mock 的定位、四项注入、收口要求；可注入 Fake Adapter、`run --mock` 等具体机制，在下一个真实的 Demo 需求中做出来、验证后再沉淀进脚手架。不预先建设通用 Mock 框架。

## 6. 操作面：run / observe / drive / deploy

Harness 面向工程运行和交付，提供四个稳定的操作入口：

- **`run`**：启动服务、执行检查或运行测试，提供稳定执行入口和固定日志路径。（探索链的 `run --mock` 见第 5 章。）
- **`observe`**：读取系统运行证据——结构化日志、关联 ID、Trace、数据库只读查询、状态 Dump、页面结果和产物信息。原则上不修改业务状态。
- **`drive`**：仅在本地开发环境中创建一次性资源沙箱，通过真实产品入口推进已批准的 Case，取证后销毁整个沙箱。
- **`deploy`**：把经过验证和批准的版本发布到目标环境——构建、打包、发布、滚动更新、健康检查、必要时回滚。部署必须能回溯版本、产物和验证证据。

### 6.1 Drive 的边界

`drive` 是本地开发阶段的操作原语，**严禁在服务侧 Test 和 Production 环境执行**。Test / Production 的回归测试需要遵守非破坏性、权限受控、数据可识别的另一套模型，不能复用本地 Drive 的"整体复制、整体销毁"语义。

给 AI 破坏性权限的安全解法不是约束它的行为（不可靠），而是约束它能触达的世界（可靠）：人工、脚本或 AI 在正常开发中产生的数据都属于受保护的永久数据；Drive 不追踪自己创建的每条记录、不做补偿恢复——它只允许连接受保护资源的一次性完整副本，结束时销毁整个副本，就天然保证不污染永久数据。

```text
受保护的本地 main 资源
          ↓ clone
一次性 Sandbox 资源
          ↓
启动一次性应用实例
          ↓
Drive → Observe
          ↓
销毁 Sandbox
```

Test / Production 环境的回归由**冒烟投影**承担：Core-Case（见 7.5 AC 节约定）在真实环境上的降级重裁——同一入口、同一 must 主链路（Playwright，必要时 Computer Use），但不注入错误与极端数据、不创建沙箱，数据必须可识别、操作必须非破坏。按判定四件套，被验证对象包含环境：本地 Drive 的绿灯不迁移到测试与生产——部署本身（新环境、新配置、真库 Migration、真实 Provider）就是新的被验证对象，必须重新裁决。8.5 要求的"发布候选必须真实调用一次外部服务"即落在冒烟投影中执行，不引入独立的 Canary 概念；部署到测试环境后、以及 `deploy` 之后的生产观察窗口，均以冒烟投影的 PASS 收口。

### 6.2 受保护资源

项目在 Harness 配置中声明需要保护的存储资源及复制方式。"保护"不是给每条数据打标记，而是**不让 Drive 应用拿到源资源的连接地址和写权限**：正常开发应用连 `main`，Drive 应用只拿到本次 Sandbox 的临时配置。

```yaml
protected_resources:
  mysql:
    source: mysql://localhost:3306/app
    schemas: [app]
    sandbox_image: mysql:8.4
    clone: mysqlsh-copy
  redis:
    source: redis://localhost:6379
    clone: empty
  cos:
    bucket: app-local
    source_root: main
    clone_root: clone-<run_id>
```

Drive 启动时执行硬校验：当前环境必须是本地、数据库必须指向临时实例、`COS_ROOT_PREFIX` 不能为 `main`。任何一项不满足立即停止，且**不提供跳过保护的参数**。

### 6.3 最小副本策略

实例与数据分开处理：Docker 负责用相同镜像和配置启动一次性基础设施实例，资源自身的复制能力负责填充数据；不复制正在运行的容器或原始 Docker Volume。

- **MySQL**：启动同版本一次性 Docker 实例，用 MySQL Shell `copySchemas` 把受保护 Schema 复制过去；复制完成后只在副本上执行未执行的 Migration。数据量大到逻辑复制成为瓶颈时，才考虑 MySQL Clone Plugin 或文件系统快照。
- **Redis**：默认启动空实例——缓存、锁、会话和临时队列本就应当可重建；只有项目明确把必要基准状态存在 Redis 时，才用 RDB 初始化副本。
- **COS**：本地数据量应保持小，直接把开发桶 `main/` 全部对象服务端复制到 `clone-<run_id>/`；全部成功才启动 Drive，失败则删除未完成的前缀。业务库只存相对 Key，`CosStorage` 按当前 `COS_ROOT_PREFIX` 统一生成实际 Key、签名地址和删除路径。

COS 根目录约定：

```text
app-local/
├── main/                         # 永久、受保护的本地开发数据
├── clone-20260715T153000-a8f3/  # 一次性 Drive 副本
└── clone-.../

app-test/
└── main/

app-prod/
└── main/
```

`main/` 在任何清理路径下禁止删除。Clone 前缀用"时间 + 随机短 ID"生成避免并发冲突；写入 `_harness.json` 记录 `run_id` 和过期时间，全部对象复制完成后写入 `_READY`。只有同时具备 `clone-` 前缀、合法 `_harness.json` 且 `run_id` 匹配的目录才允许销毁。

### 6.4 Drive 生命周期

```text
harness drive <case>
  → 校验本地环境与保护规则
  → 生成 run_id
  → 在复制窗口内暂停 main 写入
  → 创建临时 MySQL、Redis、网络和 Volume
  → 复制 MySQL Schema 与 COS main 前缀
  → 恢复 main 的正常开发写入
  → 用临时配置启动一次性应用实例
  → 用 Playwright 或必要的 Computer Use 完成 Case
  → Observe 并保存 Log、Trace、截图和测试结果
  → 按 Case Oracle 输出 PASS / FAIL / INCONCLUSIVE
  → 停止一次性应用
  → 删除临时容器、网络、Volume 和 COS Clone 前缀
```

销毁逻辑内聚在 Drive 的 `finally` 阶段：无论成败，先保存证据再销毁资源。所有本地临时容器、网络、Volume 打统一的 Harness Label；进程被强杀或断电后，下一次 Drive 启动前由内部垃圾回收清理超过保留期的孤儿资源。

### 6.5 如何证明正确

Harness 不试图形式化证明整个软件绝对正确，而是在边界明确的 E2E Case 内证明：**指定代码或产物，在指定环境和前置条件下，经过指定用户动作后，产生了产品合同要求的外部结果，没有产生明确禁止的结果，且证据完整、可信、属于本次执行。**

```text
Case 内的正确
  = 必须结果全部成立
  + 禁止结果全部未发生
  + 必需证据完整
  + 证据属于本次 Run
  + 被验证对象身份明确
```

警惕**假绿灯（False Green）**——看起来通过、实际错误：页面没报错、接口返回 200、日志没有 Error、数据库状态为 `completed`、Playwright 跑完了、AI 截到一张成功页面，都不能单独证明产品正确。典型假绿灯：页面显示生成成功但产物打不开；数据库状态"完成"但展示的是上一次运行的旧产物；日志无异常但生成了错误角色的内容。

一次正确性判定至少包含四部分（下称**判定四件套**）：

1. **被验证对象**：Git Commit、Dirty State、产物摘要、配置摘要、Migration Head、环境、Case 版本和 `run_id`——避免"验证 A、部署 B"，或把历史证据误认为本次结果。
2. **用户动作**：真实产品入口、关键输入、点击或上传动作、等待边界、最终到达状态——不能只写"验证了工作流功能"。
3. **正确性 Oracle**（判定标准）：执行前声明必须结果 `must`、禁止结果 `must_not`、超时和必需证据；产品语义以 Feature 设计决策的 PD 与 AC（见 7.5）为权威。
4. **确定性 Verdict**（判定结果）：只允许 `PASS` / `FAIL` / `INCONCLUSIVE` 三值，并保存判定所用的完整证据。

机器可读的最小 Case 示例：

```yaml
case: WF-001

entry:
  url: /workflows/<workflow_id>

actions:
  - click: 运行

must:
  - 出现属于本次 Run 的新运行记录
  - 运行在超时前变为 completed
  - 预期节点全部完成
  - 新产物数量和归属正确
  - 每个新产物都可以正常预览

must_not:
  - 出现错误提示
  - 节点永久停留在 running
  - 复用上一次运行的旧产物
  - 重复创建运行记录

required_evidence:
  - 关键动作后截图
  - 最终稳定态截图
  - 新产物可打开证据
  - 本次 Run 的 Trace 和关联 ID

budget:
  timeout: 5m
  retries: 1
```

Verdict 规则固定：

- **PASS**：所有 `must` 成立、所有 `must_not` 未发生、必需证据完整且确认属于本次 Run。
- **FAIL**：任一 `must` 不成立、任一 `must_not` 发生，或已有足够证据证明产品合同被违反。
- **INCONCLUSIVE**：环境异常、证据缺失、Trace 无法关联、超时但无法判断业务结果，或无法确认结果由本次 Run 产生。**INCONCLUSIVE 不得被 AI 解释为 PASS。**

业务正确性由用户可观察的产品结果定义；Log、Trace 和数据库证据负责确认运行归属、链路完整性和失败原因。内部状态可以否决一次验收，但不能替代外部结果。

### 6.6 统一留痕：机器裁判与人裁判共用一套模具

执行过程是有状态的，状态必须留痕。裁决链与探索链共用 6.5 的判定四件套，区别只在 Oracle 的执行者：AC / E2E 的裁判是机器，Demo 评审的裁判是人。Demo 评审按四件套留痕如下：

1. **被体验对象**：Commit + **Mock 配置摘要**。Mock 注入了什么必须记录——"在 0ms 延迟下确认的 PD"和"在 300ms 注入下确认的 PD"是两个不同的事实。
2. **体验动作**：走了哪些入口、试了哪些路径，必须包含非正常路径（错误、空态、极端数据）。
3. **待确认 PD 清单**：Demo 之前列出，等价于事先声明的 Oracle——不允许看完 Demo 再临时决定"确认了什么"（总原则第 5 条：裁判与运动员分离，对人裁判同样生效）。
4. **人的 Verdict**：对每条 PD 逐条给出 确认 / 修改 / 否决，不允许整体一句"感觉不错"。

状态流向：**Demo Run → PD 决议 → 设计决策 → AC 引用**。Demo 因此不是一次性的看片会，而是设计决策的上游生产环节，整条链有据可查。具体字段与存放位置在 Harness 实施方案中细化。

### 6.7 不提供 Reset 与 Save

不公开提供 `reset`：一次性沙箱模型中，清理是 `drive` 生命周期的结束阶段；独立的 Reset 反而带来遗漏清理、目标不明和误删永久数据的风险。

不提供 `save`：永久开发数据本就在受保护的 `main` 中；Drive 的 Clone 只是短期验收沙箱，不承担跨 DDL、业务模型和 COS 规则演进的历史存档职责。需要保留的是 Drive 的 Log、Trace、截图和结构化测试结果，而不是临时存储资源。

典型流程收敛为：

```text
run → drive（clone → act → observe → oracle → verdict → destroy）→ deploy → observe
```

后端或基础设施检查通常只需要 `run → observe`；需要通过真实产品入口推进业务状态时用本地 `drive`；`deploy` 属于高风险操作面，只作用于已批准、已验证的产物。

## 7. 文档体系

### 7.1 设计原则

Harness 文档只保留需要**跨会话、跨人员、跨版本**传递的长期语义，不把 LLM 执行过程中的临时状态固化为长期文档。文档体系要让人和 AI 快速回答：项目有什么、当前业务语义是什么、哪些约束必须遵守、历史决策为何变化、如何验收、如何按标准流程操作系统。

Spec、Plan、Progress、Review、Changelog 属于开发过程状态，由 LLM 任务、Issue、Git 和自动化报告承载，不长期维护对应文档。评审产生的有效结论直接改回设计决策（见 7.5）、领域定义、ADR 或项目规则，不保存一份容易失效的 Review 副本。

### 7.2 最小目录

```text
AGENTS.md

docs/
├── maps/
│   ├── product.md
│   └── technical.md
├── rules/
│   ├── architecture.md
│   ├── coding.md
│   ├── testing.md
│   └── deployment.md
├── domains/
│   ├── index.md
│   └── <domain>/
│       ├── domain.md
│       └── adr/
│           ├── 0001-<decision>.md
│           └── 0002-<decision>.md
├── features/
│   └── <feature>/

├── technical/

```

目录按需创建，不要求第一天生成全部空文件。只有稳定、复杂、无法从代码直接理解的全局架构和关键组件才进入 `technical/`，不为简单实现写说明书。

### 7.3 AGENTS、地图与规则

- **AGENTS.md** 是 AI 的项目入口和上下文路由，不是项目大百科：只记录必须遵守的工作规则、标准命令、修改边界、验收要求，以及各类权威文档的位置。
- **产品地图**描述产品领域、核心能力和用户入口，帮 AI 从需求定位到业务上下文。
- **技术地图**描述应用、服务、模块、基础设施及其关系，帮 AI 从业务能力定位到代码和运行入口。
- **项目规则**描述架构、编码、测试和部署的强约束；能用脚本、Lint、测试或发布门禁自动执行的规则，不只停留在自然语言（总原则第 4 条）。
- **语言约定**：AGENTS.md、项目规则、SOP、Skill 与提示词等一切约束性文本，一律用中文编写。这不是偏好，是反馈回路决策（总原则第 1 条）：模型读中英文能力无差别，而这些文本的最终审核者与维护者是作者本人，中文是作者最熟悉的语言——用英文书写只会拉长"人审核约束"这一侧的回路，还会制造中英两套口径漂移的空间。

### 7.4 领域与 ADR

**领域**是拥有独立业务语言、业务规则、状态生命周期和数据所有权的一组业务能力。领域不按前端、后端、Worker、数据库表或团队划分——那些是技术实现或组织结构。建立领域时从真实业务动作出发，检查它是否拥有独立术语、核心状态、业务不变量、数据所有权和变化节奏。领域只在真实边界出现时创建；如果一个领域的 ADR 长期充满互不相关的问题，优先检查领域是否划得过大，而不是上知识图谱。

每个 `domain.md` 保持轻量，只记录：领域为什么存在；核心概念和状态；明确不拥有的内容；统一业务语言及需避免的歧义词；与其他领域的命令、事件或数据关系。领域边界的重大拆分、合并或所有权迁移本身就是长期决策，需要形成 ADR。

**ADR**（架构决策记录）按领域维护，递增编号形成一条隐式时间链：

```text
docs/domains/workflow/adr/
├── 0001-full-workflow-retry.md
├── 0002-node-level-retry.md
└── 0003-checkpoint-resume.md
```

ADR 聚合某次长期有效的产品与技术决策，链接对应的设计决策，但不复制正文——只记录最终决策、为什么改变、新决策对旧决策的影响。每条新 ADR 必须明确说明替代了旧 ADR 的哪些语义、保留了哪些约束，不让 LLM 猜。

决策回溯的语义复杂度交给 LLM：先读领域定义，再从最新 ADR 向前读，必要时展开关联文档。工具只处理确定性的目录扫描、编号排序、全文搜索和链接校验——不建图数据库，不引入 DFS、拓扑排序、Topic 和复杂关系类型。轻量命令：

```text
harness adr history <domain>
harness adr latest <domain> --limit 5
harness adr search <domain> <keyword>
harness adr validate
```

跨领域决策只存放在主要负责的领域，其他领域链接引用，不复制；确实无法归属的系统级决策才进入少量全局 ADR。

**架构全景与演进快照。** `technical/architecture.md` 只维护当前的全景架构图，使用 Mermaid 等文本格式——模型可生成、Git 可 diff、节点名可被校验，不用手绘图片。每条架构级 ADR 定案时必须附带一张**标色增量快照**：在当次全景上以三色标出新增 / 修改 / 废弃的节点与边。历史快照随 ADR 保留、永不删除——演进路线不需要独立机制，沿 ADR 编号链回放快照即是；不另建快照目录，避免两套历史口径。

新项目或新领域启动时执行一次**立项决策**：产出全景图初版、初始 `domain.md` 集和奠基 ADR（`0001` 系列）。这是宏观架构唯一的"从零生产"环节——存量项目靠结构即提示（总原则第 4 条）承载架构，而立项时还没有存量结构可模仿，必须由架构师亲自定案。此后一切 Feature 级 TD 都是对这条链的增量记账。产物判据与 PTA 相同：只写决策，不写实现；模型能自己安全推翻的分层细节不进文档，进脚手架。

### 7.5 Feature 设计决策（PTA）

每个 Feature 维护两份文档，一进一出：

**原始需求（`brief.md`）是输入**：来自业务方或有诉求用户的几句话，只表达需求愿景，不写约束、实现和设计。保留原话、不加工——它是探索与取舍的起点，也是日后回答"当初到底要什么"的唯一凭据。

**设计决策（PTA，`pta.md`）是产出**：从原始需求出发，经思考、取舍、设计、决策后提炼出的可落地、有约束的规范——这是整个文档体系里价值密度最高的一份。它只收录已经定案的决策，每一条都不许模型自行推翻。缩写 PTA 来自它的三个决策章节的首字母——**P**D 产品底线、**T**D 技术决策、**A**C 验收标准。

它合并了传统的 PRD、技术设计和 E2E TestCase——三者本就是同一批决策的三种视角，分开维护只会产生同步成本和口径漂移（同一条决策以三种措辞散落三处，改一处漏两处）。

设计决策固定四节：

1. **背景**：为什么做、给谁用、边界在哪。（承接原 PRD 的"为什么"）
2. **PD 产品底线**：不可退让的产品决策，逐条编号。Demo（第 5 章）产出的 PD 决议直接落在这里。（承接原 PRD 的产品合同）
3. **TD 技术决策**：只记录难以回头、跨模块或影响长期演进的技术选择及其理由；可逆的实现细节交给模型，不进契约。（承接原技术设计的关键取舍）
4. **AC 验收标准**：从真实用户入口、以黑盒方式定义"什么算对、什么算不合格"，包含 must / must_not、超时边界和必需证据；是 6.5 Oracle 的权威来源，机器可读的 Case 文件由本节展开生成。（承接原 E2E TestCase）

TD 节的固定首条是**架构位置图**：从全景架构图（见 7.4）裁剪出的本需求视角位置图——只允许引用全景中已有的节点名，标色画出本需求触及的层次、模块与依赖方向。它既是架构师决策的关键背景，也是升级规则的**检测器**：位置图只用到现有节点与现有边，说明架构未动，TD 无需升级，画完即背景信息；出现新节点、新依赖边或跨领域调用，说明本需求改变了架构，必须走架构变更环节——产出或修订 ADR 与全景标色快照，PTA 中只留决策一句话加链接。**不允许架构语义只存在于某个 Feature 的 pta.md 里**：Feature 文档随 Feature 沉底，架构语义不能跟着沉底。

AC 节必须恰好指定一条 Case 为 **Core-Case**（F0 正向主链路），并声明它在 test / production 环境上的冒烟投影（见 6.1）：同一条 Case、must 子集裁决，不另写第二份措辞，避免同一链路两处口径。

写多细的判据只有一条：**设计决策只写决策，不写实现。** 一条内容如果模型可以自己安全地决定或推翻，它就不属于设计决策。

不改变产品语义和长期技术决策的小修复，直接改代码和已有测试；只有改变产品行为、领域边界、架构或长期约束时，才更新设计决策和 ADR。

样例（TalkTa 发音评估）——先看输入：

```markdown
# 原始需求：发音评估
来源：教研组（2026-07-14，原话记录）

学员跟读完一句话，希望马上告诉他哪个词读错、哪个词漏了，
像老师当场圈出来一样。
最好能按"这节课练句子还是练单词"分开看效果。
别只给一个总分，分数解释不了问题。
```

再看从它提炼出的产出：

```markdown
# 设计决策（PTA）：发音评估 v1

状态：已定案（2026-07-21）｜输入：brief.md｜关联 ADR：0003-语音供应商选型

## 1. 背景
口语课学员跟读后需要即时、逐词的发音反馈。
本期只覆盖英文句子/单词跟读，不做自由对话评分。

## 2. PD 产品底线
- PD-1 评估结果必须落在教学目标上：按 sentence / vocabulary
  两类目标分别呈现，禁止只给一个全局总分。
- PD-2 漏读（Omission）按错误处理并高亮到词；
  系统原因导致的静音不得计为学员错误。
- PD-3 跟读中途停顿 ≤ 3 秒不判定为结束，不打断学员。
- PD-4 评估失败时明确告知"本句未评估成功"，禁止展示任何估算分数。

## 3. TD 技术决策
- TD-1 发音评估采用 Azure Speech Pronunciation Assessment，
  不自研声学打分。理由：对齐与打分自研成本高且质量不可控。
  排除的备选：Whisper + 自研音素对齐。
- TD-2 每个 prompt 新建 recognizer，走 recognizeOnceAsync；
  不复用 recognizer 生命周期。理由：连续识别模式下
  Miscue 统计存在跨句污染（官方 SDK 已知问题）。
- TD-3 EnableMiscue 固定开启；Omission / Insertion 的裁决
  在服务端归一，前端不重算。
- 不收录（反例）：录音上传的重试次数、波形动画的实现方式
  ——模型可自行决定、随时推翻，不属于设计决策。

## 4. AC 验收标准
- AC-1（对应 PD-3）真实麦克风入口朗读目标句，中途停顿 3 秒。
  must：评估继续并返回逐词结果；must_not：会话提前结束。
  超时：10s。证据：评估结果 JSON + 界面截图。
- AC-2（对应 PD-2）漏读句中一个单词。
  must：该词标为 Omission 并高亮；must_not：计入其他错误类型。
- AC-3（对应 PD-4）断网状态下提交跟读。
  must：提示"本句未评估成功"；must_not：出现任何分数。
```

注意样例里的几处对应关系：原始需求的每句话都能在 PD 里找到归宿（"圈出来"→ PD-2、"分开看效果"→ PD-1、"别只给总分"→ PD-1/PD-4）；每条 AC 回指一条 PD，并事先锁死 must / must_not、超时和证据（6.5 的 Oracle）；TD 记录理由和被排除的备选；"不收录"反例演示粒度判据——模型可自行推翻的内容不进 PTA。

### 7.6 TestCase 边界

文档体系只维护端到端黑盒验收——即设计决策的 AC 节，不维护单元测试、API 测试和集成测试的文档。白盒测试仍必须按风险和 TD 编写，但与代码放在一起，由测试框架和 CI 自动发现，不复制成长期文档。

AC 中的每个 Case 只描述用户入口、前置条件、操作步骤和外部可观察结果，是产品行为"如何证明正确"的权威合同。每个 Case 必须事先明确必须成立的结果、禁止出现的结果、超时边界和必需的黑盒证据（对应 6.5 的 Oracle）——不能运行完再由 AI 临时挑证据或降标准。

Log、Trace 和数据库状态用于证明证据属于本次执行、检查运行完整性、诊断失败；不把内部实现细节写成黑盒产品合同，也不能用"日志没有 Error""数据库状态为 Completed"替代"用户真正获得了正确结果"。

### 7.7 API、DDL 与权威来源

不人工维护 API 和 DDL 文档。API 的权威来源是路由代码、OpenAPI Schema 和运行中的接口；数据库结构的权威来源是 Migration、ORM Model 和真实数据库 Schema。Harness 提供机器可读的实时查询入口：

```text
harness observe api
harness observe db schema
harness observe db migrations
```

只有对外公开或跨团队长期承诺的 API Contract 才需要写进 PRD 或技术设计。代码实现过程由 Git 保存；发布记录和变更信息从 Git、ADR 和发布产物中生成，不手工维护 Changelog。

### 7.8 SOP

运维和部署统一使用 SOP（标准作业程序），不额外引入 Runbook 概念。项目规则说"什么允许、禁止、必须满足"，SOP 说"在具体场景下按什么顺序执行"。

每份 SOP 至少包含：适用范围、执行前提、权限和输入、标准步骤、每步预期结果、停止条件、结果验证、失败处理、回滚入口、需要保存的证据。可执行逻辑沉淀在 `run / observe / drive / deploy` 等稳定命令中；SOP 只说明何时执行、由谁批准、调用哪个入口、如何判断成功——避免复制大量容易漂移的 Shell 命令。

## 8. 可复用代码组件

### 8.1 设计原则

可复用组件统一沉淀在托管于 Gitee 的 `harness-libs` Git Monorepo 中，按能力和语言发布为多个独立 Package。仓库边界用于统一合同、开发、测试和发布；Package 边界用于隔离依赖、版本和升级。不建包含一切的 `harness` 大包，也不在初期为每个小组件拆独立仓库。

进入公共库的标准：跨项目必须保持一致、修复后应同步惠及所有项目、接口相对稳定、**不包含业务语义**的机制。项目结构、领域模块、页面、工作流样例和仍需大幅修改的框架胶水留在脚手架或 `examples/`，由 AI 结合当前项目参考改写，不复制公共库内部实现。

公共能力只负责技术机制，项目负责业务语义。例如 Observability Package 负责 `trace_id`、上下文传播、结构化日志和脱敏；项目负责 `workflow.completed` 这类领域事件及其业务字段。

### 8.2 公共库结构

```text
harness-libs/
├── docs/
│   └── contracts/
│       ├── observability.md
│       ├── trace-context.md
│       ├── error-model.md
│       └── cos.md
├── contracts/
│   ├── log.schema.json
│   ├── error.schema.json
│   ├── trace.schema.json
│   └── cos.schema.json
├── python/
│   ├── pyproject.toml
│   ├── uv.lock
│   └── packages/
│       ├── harness-observability/
│       ├── harness-cos/
│       └── harness-llm-client/
├── typescript/
│   ├── pnpm-workspace.yaml
│   ├── pnpm-lock.yaml
│   └── packages/
│       ├── observability/
│       └── cos/
├── tools/
│   └── harness-cli/
└── examples/
    ├── fastapi/
    ├── vue/
    └── electron/
```

Shared Contracts 属于公共库的文档体系：`docs/contracts/` 解释语义、设计理由、使用规则和示例；`contracts/` 保存可被测试和代码读取的 JSON Schema。机器字段和格式以 Schema 为权威，语义解释以文档为权威；各语言 Package 必须通过同一组合同测试。下游项目不复制整套公共文档，只记录使用的 Package 版本、本项目扩展字段和特殊约束，由 AGENTS.md 路由到公共库文档。

Python 使用 uv Workspace，TypeScript 使用 pnpm Workspace；同一仓库中的各 Package 独立版本、独立构建、按需发布。

### 8.3 第一批公共能力

第一批只建设已经明确跨项目复用、且合同相对稳定的能力：

- **`harness-observability` / `@harness/observability`**：统一单行 JSON 日志、Trace ID、HTTP 与异步任务上下文传播、Python `contextvars`、Node.js `AsyncLocalStorage`、错误结构化、脱敏、stdout 输出和测试用内存 Sink。不负责 CLS 上传、日志存储、Dashboard 和业务事件定义。
- **`harness-cos` / `@harness/cos`**：统一封装腾讯云 COS 官方 SDK 和通用对象语义。Python 侧承担服务端操作和临时凭证下发；TypeScript 侧用受限短期临时凭证直传，提供上传进度、取消、分片、有限重试、凭证刷新、统一结果、错误与 Trace 关联。长期 Secret 不进前端；具体实现以 `dh` 项目的成熟实践为重要参考。
- **`harness-llm-client`**：LLM Proxy 的 Python Client，统一鉴权、普通与流式调用、超时、取消、安全重试、Trace 传播、Provider Request ID、Token/成本结构、错误模型和测试 Fake；不在每个项目重新适配模型供应商。

前端 HTTP Client、Electron Runtime、UI 组件库和 Harness CLI 在真实项目中继续验证，合同稳定后再升级为正式 Package。数据库、Redis、Repository、Service、CRUD、工作流、领域事件和业务状态机不做无条件公共抽象；禁止建立无法表达清晰能力边界的 `harness-utils`。

### 8.4 Package 与脚手架的边界

代码进入公共 Package 前，至少满足：

- 已在两个真实项目中使用或验证，或跨项目一致性已是明确硬约束。
- 不包含具体领域概念，输入输出合同相对稳定。
- 外部差异可以通过配置或窄 Adapter 表达。
- 能独立测试，且修复后确实需要所有下游共同升级。
- 独立版本带来的统一修复收益大于依赖升级成本。

不满足的先留在脚手架或 `examples/`。推荐"机制 Package 化、接入代码项目化"：公共库提供稳定 API，项目只保留少量 Service 名称、环境配置、业务事件和领域字段的组装代码。

### 8.5 测试与发布

每个 Package 至少具备：单元测试、类型检查、Lint、兼容版本矩阵、构建测试、Fake/TestKit 和最小接入示例。跨语言能力必须跑合同测试——例如 Python 与 TypeScript 生成的日志都符合同一份 `log.schema.json`，且能被 `harness observe` 正确解析。

COS、LLM 等外部能力采用"大量确定性 Fake 单测 + 少量真实服务集成测试"；真实服务不作为默认开发内循环，但发布候选版本和关键兼容性变更时必须执行（裁决链上不许有假）。

每个 Package 独立采用语义化版本：Patch = 向后兼容的修复；Minor = 向后兼容的新能力；Major = 破坏性修改。发布后不可覆盖或重写同一版本。源码和 Release Tag 托管在 Gitee；构建产物发布到标准 Python/npm Registry（Registry 部署方式单独确定）。早期直接引用 Git 时，只能固定不可变 Tag 或 Commit，禁止依赖 `main`。

业务项目不手工维护 Changelog，但公共 Package 必须提供可生成的版本说明：影响哪些 Package、兼容性、修复、新能力和迁移要求——这是下游安全升级的必要合同。

### 8.6 下游更新机制

公共库更新不主动改写或强推下游仓库，通过"发布版本 → 下游升级 PR → 下游门禁"传播：

```text
公共库 PR
  → Package 单测、合同测试和构建
  → 发布新版本与不可变 Gitee Tag
  → 下游定时检查新版本
  → 更新依赖声明和 Lockfile
  → 推送升级分支并创建 Gitee PR
  → 下游运行类型检查、单测、集成、构建和关键 E2E
  → 验证通过后合并、部署或回退
```

为避免绑定 GitHub Dependabot，公共工具提供平台无关的依赖命令：

```text
harness deps check
harness deps upgrade <package> [version]
```

由 Gitee 定时流水线或现有 CI 周期执行检查；发现新版本后创建升级分支，更新 `pyproject.toml` / `package.json` 与 `uv.lock` / `pnpm-lock.yaml`，跑最短门禁，再通过 Gitee OpenAPI 创建 Pull Request。初期不自动合并：Patch 自动创建 PR，稳定后才允许全部门禁通过时自动合并；Minor 需要 AI 或人工检查版本说明；Major 必须建立显式升级任务并验证迁移；安全修复走高优先级最短路径。

涉及 COS、LLM、Electron Updater 等外部或高风险能力时，先发 Beta 到试点项目，完成真实集成和 E2E 后再发 Stable，逐步向其他下游创建升级 PR。下游 Lockfile 是实际部署版本的权威；新版本有问题先回退依赖与 Lockfile，公共库另发修复版本，不修改已发布的旧版本。

## 9. 建设路线

Harness 的建设顺序由总原则第 1、2 条决定——按反馈回路的价值排序，由真实项目拉动：

1. **操作面（run / observe）**：模型能跑、能看，是一切自主性的起点。
2. **同构基础设施**：反馈保真，模型自查才可信。
3. **文档体系最小集**：AGENTS + 地图 + 规则，让模型进得来、路由得到。
4. **drive 与 Oracle/Verdict**：裁决链闭环，验收可信。
5. **探索面机制（Mock / Demo）**：由第一个真实的 Demo 需求拉动落地。
6. **公共库**：从两个以上真实项目中沉淀，最后成形。

每一项立项时回答同一个问题："它缩短了哪条反馈回路？"答不上来，就不做。
